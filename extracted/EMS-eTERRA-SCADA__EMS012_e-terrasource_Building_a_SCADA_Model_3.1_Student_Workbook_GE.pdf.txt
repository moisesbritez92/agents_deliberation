Scope of this Course 
This course covers the basic data structures and associated data attributes that condition the manner in which the 
e-terrascada subsystem gathers and processes real-time measurements from various data sources. This data is 
provided to ALSTOM GRID software via a data model that is maintained via the e-terrasource product. Therefore, this 
course looks at SCADA data from the e-terrasource perspective, making extensive use of the e-terrasource user 
interface. The Alarm server model is also examined through the e-terrabrowser user interface. Tips for customizing 
e-terrascada are also presented.  
 
Content and Organization 
Building a SCADA Model explains how to create and modify parameters affecting real-time processing of data objects 
in the SCADAMOM database. Following the overview, the following topics are covered: 
• SCADA as an Alarm Client 
• Status Points (Discretes) 
• Analogs 
• Accumulators 
• Controls 
• Special Controls 
• Calculated Measurements 
• Topology Processing  
• Historical Data Recording 
• Communication and RTU Modeling 
• InterSite Operations Modeling 
• SCADA Online Editing 
• Deploying the Model  
• Efficiently Developing the Model 
The lab sessions are based upon an existing, fictional, power system’s SCADA model, which is mapped to a 
corresponding Generation and Network model. This course concentrates on only the SCADA model attributes. The 
Generation and Network data attributes are left for later courses

Course Objectives 
After completing this course, students will be able to: 
• Define the three components of the SCADA application 
• Describe the data structures present in the SCADAMOM database 
• Explain from the figure how e-terrascada interacts with ALARM service 
• Navigate to and edit (insert, delete, modify) SCADA DISCRETES  
• Navigate to and edit SCADA ANALOGS  
• Navigate to and edit SCADA ACCUMULATORS  
• Navigate to and edit SCADA CONTROLS  
• Navigate to and edit SCADA SPECIAL CONTROLS  
• Navigate to and edit SCADA CALCULATION TEMPLATES  
• Navigate to and edit SCADA DEVICE TOPOLOGY 
• Describe how e-terrascada processes device energization and connectivity 
• Navigate to and edit SCADA Historical Data recording parameters (HDR) 
• Navigate to and edit SCADA COMMUNICATION TOPOLOGY 
• Navigate to and edit SCADA RTU TOPOLOGY 
• Explain how data is sent and received with other sites (ISD) 
• Navigate and use the displays used for Online SCADA Editing 
• Describe how a new SCADA model is deployed 
• Describe the early design factors for efficient SCADA modeling

e-terrahabitat modeling workstation, have access to a device or devices that can serve as e-terrahabitat 
console/station and e-terrasource clients, and have access to online e-terrascada documentation.

Evolution to e-terrasource:
e-terrasource takes the approach that a model is a business system for 
model construction and maintenance. It interacts with other business 
systems requiring business system models. Transmission network models, 
for example, can be managed by e-terrasource and supplied to EMS, 
market and planning systems from e-terrasource.
e-terrasource is a system description. The transmission system model 
defines the need for a certain kind of equipment in a particular substation 
in a particular relationship to other elements of the transmission system. A 
position in the system can be planned, with no actual asset corresponding -
or a position can be in a neighbor’s territory.
• e-terrasource stores all of the system descriptive data in a relational 
database (RDBMS).
• From there, it is deployed to the HDB clones using the Transformation 
Subsystem.

Note: SCADA is one of many clients of ALARM. 
1. Registered Client decides what is worthy to report.
• Client creates an EVENT block (category, exception, location, area, text, options).
• Client makes an API call to alarm – PostEvent.
2. Alarm- wakes up and processes the Event from some client.
• Updates the ALARMLST database in the ALARM clone.
• Uses PERMIT to validate the client “AREA” in the event.
• Uses the ALARM modeling database to validate the CAT, LOC, EXC, options.
3. ALARM - Makes an API call to LOGMAN (if used).
4. ALARM - Issues an audible tone (via Webf g) to any workstations modeled as HORNS
5. ALARM - Records the event in its ALARMARC recording file (for history).
6. System Operators - from an ALARM or CLIENT screen, acknowledge (indicate that they have 
seen) the Alarm.
7. ALARM - Updates its own database, records the ACK from the SC action - Webfg or rule.
8. ALARM - if so configured, wakes up the client - “your event has been ACKed”.
9. System Operators -to remove the alarm from their displays: DELETE / PURGE alarm.
10. ALARM - Deletes the alarm from its database (ALARMLST), records the operator action.
• No notification of DELETE to client - (by design) only effect is within ALARM.
• If the client wants some DELETE behavior, client software has to perform that.

PROXYSRV Databases
The PROXYSRV application uses its own databases, called “PROXYSRV” and “PROXYLOG”.
• PROXYSRV - Contains connection parameters for handling and managing connection 
requests. It also contains parameters for processing Alarm data.
• PROXYLOG - PROXYSRV log database.
PROXYSRV Savecases
The only savecase associated with the PROXYSRV application is called “PROXYSRV”, and it 
is present in the PROXYSRV codeset.
PROXYSRV Tasks
The PROXYSRV application performs the following primary functions:
• It processes connection requests from its clients using TCP/IP, and it manages and 
administers the established connections.
• It allows clients (applications) to exchange data using the InterSite Data (ISD) protocol.
• If enabled, it receives alarm messages from alarm server, formats the alarm data, and 
then posts the alarm message.

Task 2: Setting Inhibit Definitions 
The SCADA database models what operator inhibit activity will accomplish. 
Remember there are two sets of five flags that control this: one set to 
permanently inhibit alarm processing, and one set that allows the operator a 
binary control of SCADA alarm processing (inhibit/un-inhibit). 
Setting the global Configuration values of these five flags defines the default 
behavior of how e-terrascada posts events to Alarm. These flags can be 
overridden on an object-by-object basis, which we will learn how to do in later 
units. The five global flags are: 
• Default Inhibit Logging: When selected, an inhibit action by the 
operator will prevent any events from being reported to Alarm by the 
e-terrascada client. This will cause loss of history while the data object 
in question remains inhibited. This implicitly prevents tones from being 
issued as well. 
• Default Inhibit Unacknowledged Condition: When selected, the 
e-terrascada client issues alarms on the inhibited object as pre-
acknowledged. 
• Default Inhibit Alarm Abnormal: When selected, the e-terrascada 
client issues alarms on the inhibited object without any indication that 
the object is in an abnormal condition. (The Alarm Server will not 
recognize an object moving to an abnormal condition.) 
• Default Inhibit SCADA Abnormal: This is a client-only behavior 
modification. When selected, if the e-terrascada client issues an alarm 
on an inhibited object, the object does not get classified as abnormal, 
thereby keeping the object off the exception list. 
• Default Inhibit Tone: When selected, the e-terrascada client 
suppresses the issuance of audible tones when issuing alarms on an 
inhibited object.

the operator’s inhibit action to NOT prevent abnormal objects from appearing 
on the SCADA exception list.

Lab 3: SCADA Status Point Modeling 
Lab Objectives 
After completing this lab, you will be able to: 
• Alter a Status Point Record 
• Enable MCD (Momentary Change Detection) processing for a status 
point model 
• Modify an Inhibit Definition for a particular status point in your model 
• Create a conditional alarm based on a status point value 
• Save and validate your work 
In order to cover these points, assume your manager has given you the 
following information: 
The two-state line switch 3032 at the Lakeview substation is being replaced 
with a three-state motor-operated switch, and the relay at the RTU being used 
is capable of sending MCD (momentary change detection) information for 
alarm purposes. 
Although the global inhibit definition for a SCADA point allows the operator to 
inhibit all portions of the alarm processing (except for preventing abnormal 
objects from appearing on the e-terrascada exception list, as you completed 
in Lab 2), for this new switch, the operator is not to be permitted to inhibit the 
issuance of the alarm. 
The alarming for this line switch needs to be made conditional on the position 
of the other line switch at the station (LS 2931). An alarm should not be issued 
on switch 3032 unless switch 2931 is OPEN (bit position 00).

Lab 13: Efficiently Developing the Model 
Templates are a very powerful tool for building models. A template is a group of 
related records that represents a reusable modeling pattern. A template can be 
repeatedly instantiated to quickly build a model. For example, templates can be used 
to represent a prototypical substation, an equipment group or bay, or a single switch. 
Templates can also have parameters associated with them. When the template is 
used to create an instance, the user is prompted to enter values for the template’s 
parameters. These user-entered values can be used to derive many of the instance’s 
properties. For example, the user could enter an “Equipment Name,” which is used to 
populate many of the names of the instance records. 
Instances that are created from templates retain information about the originating 
template. This information can be viewed at the top of the property sheets 
 
Lab Objectives 
After completing this lab, you will be able to: 
• Use the Template Management Environment to create and maintain 
templates 
• Create a template to create a simple template 
• Use a template to create a device in the model 
 
In this lab, you will create a template from a breaker defined in the HEARN 
substation along with its whole hierarchy. Then you will instantiate a similar 
breaker in the same substation.

Task 6: Defining the Template Parameters 
Template parameters are a powerful feature that can simplify modeling tasks 
for users. In a typical template, there may be many properties on several 
records that are identical (or very similar). For example: 
If a template represents a piece of equipment, there may be many records 
that can have their names derived by a naming convention based on a single 
user-entered “equipment name.” 
Parameters can also be used with metadata calculations to set certain 
properties. A single, user-entered “Voltage Level” parameter could possibly be 
used to derive values for ratings, limits, and alarm categories. 
Judicious use of template parameters can allow you to have a small number 
of powerful templates, instead of having many similar templates that vary in 
small ways.

Summary 
SCADA topology is used to monitor connectivity and energization at modeled 
locations throughout your SCADA model. Normally, KV analog measurements 
are added to devices and specified as measurement nodes. These 
measurement nodes are linked together from device to device by entering 
local/near node specifications and far node specifications for the devices 
involved. Devices that span substations between the measurement nodes are 
given a far station as well. 
A correct topology model will allow the SCADA topology processing to alert the 
operators to islands and dead power equipment.

Each sequence has three basic steps, plus some optional ones:
1. Produce CIM/XML that represents the model data in the workspace. The 
CIM/XML Import/Export service creates the CIM/XML using a CIM profile 
called "ETS." The same ETS profile is used regardless of the HDB 
database that is being processed, and it contains all modeled fields -
nothing is filtered out. So, whether you intend to populate only NETMOM 
or only ALARM, the same profile is used. Refer to CIM/XML Import/Export 
for more information on CIM profiles.
2. Feed the CIM/XML data to the tr ansformation subsystem and produce 
data that can be loaded into an HDB database. For each supported HDB 
database, the transformation subsystem has modules that contain 
instructions on how to convert the e-terrasource data into HDB data (and 
vice versa for imports). 
3. Load the resulting HDB data into a clone or savecase. 
4. Optionally, e-terraplatform validation programs can be executed, and 
5. The savecases can be compressed into a zip archive.

validation rules that are associated the requested validation sequence, and also 
associated either directly or indirectly with the change items in a project. 
Workspace validation is executed upon user request. Workspace validation checks all 
of the workspace data against the validation rules that are associated with the 
validation sequence that was requested.

One of the main purposes of e-terrasource is to supply EMS models to 
e-terraplatform. Although the particulars regarding target environments (e.g., test vs 
production) and modeling business processes may vary widely from organization to 
organization, the basic concept is the same: extract a portion of the model from 
e-terrasource, transform it, and place it into an e-terraplatform HDB database. 
Imports in e-terrasource simply work in the opposite direction.
